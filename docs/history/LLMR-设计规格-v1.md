# LLMR 设计规格 v1

> **LLMR = Agent Character Tool** · DSH 的第二个大型插件（第一个是 DET）
> 状态：正式设计稿 · 待用户确认后冻结 schema
> 取代：`LLMR-设计评审-01.md`、`LLMR-架构共识-02.md`、`LLMR-输出契约提案-01.md`

---

## 0. 定位与不做什么

### 核心主张

> **用「人工设计的固定工作流 + 硬编码调用的隔离容器」取代「通用 agent 的自主工具使用」。**

大多数 agent 框架在**加自主性**；LLMR 在**减**。这是它与世界分歧的根本点，也是它全部卖点的来源：

| 收益 | 机制 |
|---|---|
| 可预测、不跑偏 | 流程硬编码，模型没有自由发挥的余地 |
| 省 token | 不用把工具表塞进上下文，不用反复推理"该调什么" |
| 注意力集中、提升性能 | 每个容器上下文窄、工具面窄、无关内容进不来 |
| 可审计 | 能力是设计期静态绑定的一张表 |
| 人机界面匹配 | 界面绑定工作种类，不是"一个通用的臃肿 AI" |

「避免干扰」适用于**两个对象**：模型（推理质量）与用户（操作效率）。

### 明确不做

1. **不做通用 agent**——不追求"什么都能干"。装上 LLMR 不等于变万能。
2. **不自动生成 SWF**——AI 的唯一产物是 TWF（临时草稿）。SWF 永远是人的产物。
3. **不改变 DSH 原生主导航**——不 shadow `sidebar` / `sidebar.workspaces`。
4. **不发明新运行时**——SWF 是数据，执行尽量落在 DSH 现有 seam 上。

### 目标场景与门槛（必须明说）

LLMR 面向**中型/大型、任务性质明确、流程可复用**的工作。

**但它的作者门槛很高**：不能写 SWF 的用户只剩三条路——拷大佬的 / 提 issue 求作者 / 用 TWF 兜底，而**作者是瓶颈**。

> 因此对外描述必须是：**LLMR 是给"有能力定义自己工作流的人"的工具**，
> 而不是"装上就什么都能干"的通用 AI。否则用户会拿它当通用工具用然后失望。

## 1. 术语表

| 术语 | 全称 | 定义 |
|---|---|---|
| **LLMR** | Agent Character Tool | 本插件 |
| **AMZ** | AgentMemoryZone | 硬编码、隔离、工具与权限**静态绑定**的执行容器 |
| **SWF** | StableWorkFlow | **人工设计**的固定工作流（不可变） |
| **TWF** | Temporary WorkFlow | DIR 运行时构造的**临时**工作流（兜底） |
| **CSP_AMZ** | Change-SystemPrompt AMZ | TWF 构造的、**只改提示词、不提权**的 AMZ |
| **AGT** | Agent | 面向用户的角色，**绑定一个交互页面**，进入 SWF 后 stable |
| **DIR** | Director | SWF **之外**的特殊 AMZ：负责检查与造 TWF |
| **WFW** | WorkFlowWorker | 执行容器全对话的视图 |
| **WPC** | WorkPowerControl | 权限与工具调用锁的视图 |
| **TCP** | Tool Change Prompt | `step` 注入的工具变更载荷 |
| **SCP** | System-prompt Change Prompt | `step` 注入的系统提示变更载荷 |
| **标号** | — | 已转成模型可读的**信息段的序号** |
| **段** | — | 信息段库中的一条模型可读资料 |

> **命名注记**：`SCP` 是**载荷**（`step` 注入的东西），`CSP_AMZ` 是**容器类型**。
> 两者同族不同层。建议正式定名时统一前缀，避免与既有 `TCP/SCP` 混淆。

## 2. 架构总览

```
用户
 │
 ▼
[分级]  模型自评 · prompt 极干净 · 不给工具
   小 ──▶ 常规直跑（LLMR 零介入）
   中 ──▶ 判任务性质（编程/办公/…）──▶ 进入对应 SWF
   大 ──▶ 先与用户多轮对话判性质 ──▶ 进入对应 SWF
 │
 ▼  ══════════ 判定之前 = LLMR 唯一的「流动期」 ══════════
 │
进入 SWF  ──▶ 一切固定（AGT / UI / AMZ / 工具 / 权限 / 流程）
 │
 ├─ AGT 与这个人机交互页面**绑定**，此后 stable，不再变
 │
 ▼
AGT ──▶ DIR（SWF 之外的特殊 AMZ）
          │  职责：检查现有 SWF 够不够用
          ├─ 够 ──▶ 执行该 SWF
          └─ 不够 / 没有 ──▶ 造 TWF  ⚠ 兜底
                                · DIR 提示词明确"实在不行，不要构建 TWF"
                                · 默认**必须请教用户**（另有开关允许自行设计）
                                · 结构受限：只能产 CSP_AMZ（只改提示词，不提权）
                                │
                                └─ 用户觉得好用 ──▶ 晋升为 SWF
 ▼
SWF / TWF = 硬编码的有向图
            边 = 「上一步 → 下一步」关系
            条件 = 硬编码判断（**不是 AI tool use**）
 ▼
AMZ × N    硬编码调用 · 高度固定 · 高度隔离
```

## 3. 入口与分级

| 规模 | 路径 |
|---|---|
| **小** | 不启动 LLMR 任何机制，常规直跑。LLMR **零开销、零存在感**。 |
| **中** | 判任务性质 → 进入对应 SWF |
| **大** | 先与用户**多轮对话**判性质 → 进入对应 SWF |

- 分级由**模型自评**完成，prompt 要求「快速决定、非常干净、**不提供工具**」。
- 上一轮设想的"分级还要选 SWF"**不存在**：分级只判性质，**选 SWF 是 DIR 的职责**。
- 判错的升降级逃生门：**待定**（见 §16）。

## 4. AMZ 规格

### 4.1 本质

> **一个用自然语言当参数的硬编码工具。**

```
AMZ:  f(资料标号, 诉求) ──▶ 成品
      内部：固定 SystemPrompt + 固定工具表 + 固定权限 + 固定模型
      外部：什么都看不见（高度隔离）
```

### 4.2 与 AP（agent preset）的区别

| | AP | AMZ |
|---|---|---|
| 性质 | 通用、可组合 | 固定、封闭、单一能力 |
| 工具面 | 宽 | 极窄（如"几乎只有 word 编辑器"） |
| 类比 | **岗位** | **工装夹具** |

### 4.3 六字段

```yaml
amz:
  id: write_word
  prompt: ...            # 固定 SystemPrompt
  tools: [docx_write]    # 固定工具表 —— 必须是「能完成任务的最小集」
  permits: [...]         # 与 tools 静态绑定的权限
  model: deepseek-v4-pro # 固定模型
  output:                # ← 第六字段（输出契约）
    body: free           # 正文保持自由形式，不结构化
    signal:              # 可选；仅在该 AMZ 有分支出边时需要
      fields:
        need_word: bool
        refs: int[]
      encoder: self      # self | rule | weak | pipe（缺省继承全局）
```

### 4.4 四型

| 型 | 说明 |
|---|---|
| **ttc** | 无状态工具执行器。一进一出，轮间不继承记忆，高注意力，专做"半成品→成品"。 |
| **exp** | 固定领域专家。 |
| **pipe** | **转译器**（不是隔离器）。把 A 的输出重写成 B 能接住的形式。是一次真实 LLM 调用，要记账。 |
| **step** | 从已有模型端点复制，注入 TCP + SCP。 |

> **⚠ `step` 不省钱**：注入 TCP/SCP 会让请求从第 0 位分叉，继承来的历史**吃不到任何前缀缓存**。
> 它的价值是**信息保真**（省掉一次有损总结），不是便宜。**必须写进 DIR 的规划知识。**

### 4.5 调用方式

**硬编码调用**——模型手上**没有**"随便调一个盒子"的通用口子。

### 4.6 CSP_AMZ（TWF 专用）

TWF 构造的 AMZ **只能是 CSP_AMZ**：**修改面仅在提示词，不触碰工具与权限**。

> **能力边界由人工在设计期钉死；TWF 只动"怎么说"，不动"能做什么"。**

提权之所以不可能，不是因为 TWF 被限制，而是因为 **CSP 的修改面根本不在能力那一侧**——工具表和权限**不在 prompt 里**，是绑定死的。

**但这个保证有前提**：

> **每个盒子的工具面必须足够窄。** 工具面越宽，CSP 的保证越弱。

反例：某盒子带 `fs` + `pwsh`。CSP 没给它任何新权限，但一句被改过的 prompt 就能让它删文件——
**这不是提权，是"越权使用"**：用了它本来就有、但设计者从没打算让它用的能力。

→ 所以 **"几乎只有 word 编辑器"不是一句设计描述，它是 CSP 安全性的前提。**

## 5. SWF 规格

### 5.1 六字段

| 字段 | 说明 |
|---|---|
| 调用方法 | 怎么被调起：名字、适用条件、入口参数 |
| SystemPrompt | 每个 AMZ 各自的系统提示 |
| tool available | 每个 AMZ 的工具表白名单 |
| 调用顺序 | AMZ 之间的执行次序 / 依赖图 |
| model 结构 | 哪一步用哪个模型 |
| **UI** | **一个交互页面定义**（见 §11） |

```yaml
swf:
  id: review_paper
  invoke:  { when: ..., args: [...] }
  amz:     [ ... ]            # §4 的容器列表
  order:   [ {from: plan, to: write, when: signal.need_word} ]
  models:  { ... }
  ui:
    page: [AGT, WFW, DIR, WPC]   # 进入 SWF 后固定
    fallback: native             # 没有合适页面时回退 DSH 原生
```

### 5.2 三条不变式

1. **SWF 不可变**——DIR **不修改** SWF，只能在"复用"和"另造 TWF"之间选。
2. **边是硬编码的**——"上一步 → 下一步"关系，**不是**模型自主的工具调用。
3. **有分支的边组必须有 `else`**（default 边）——它是失败策略的落点。

### 5.3 分支：硬编码判断，不是 AI tool use

「某几个**规划 AMZ** 的输出可以激活 word 制造 AMZ」——这是**上一步→下一步关系**，条件也是硬编码的。

**层级区分**：SWF **内部**有规划 AMZ（其输出可决定走哪条边）；**DIR 在 SWF 之外**（只判断"该不该用这个 SWF"）。两者层级不同，DIR 从不进入执行。

### 5.4 截取方式（5 种）

| # | 方式 | DSH 现成机制 |
|---|---|---|
| ① | 只取输出 | 一次性 subagent 返回最终文本 |
| ② | 整个 | `sessions.fork(source)` 不带 boundary |
| ③ | 取到某断点 | `sessions.fork(source, **boundary**)` ✅ 原生 |
| ④ | 取某对话段 | ❌ **做不到**（fork 只能取前缀；`compactRegion` 是压成摘要） |
| ⑤ | 转译 / 总结 | `pipe`，或 `compaction` |

## 6. TWF（Temporary WorkFlow）

- **兜底设计**：SWF 无法使用时才走。
- DIR 的提示词**明确要求"实在不行，不要构建 TWF"**。
- 默认**必须请教用户**；另有开关决定是否允许 DIR **自行设计**。
- **结构受限**：只能产 CSP_AMZ（§4.6），因此**不可能提权**。
- 用户觉得好用 → **晋升为 SWF**。

> **TWF 路径的诚实定位**：它实质就是"普通 agent 模式"，只是包装成 SWF 的样子。
> **"高度固定 / 高度隔离"在 TWF 路径上不存在。** 安全模型不得假装覆盖它。

**晋升 = SWF 库唯一的人工审查点**，因此建议：晋升时必须**展示 DIR 生成的 prompt / 接线差异**供人过目。

---

## 7. DIR（Director）

- SWF **之外**的一个**特殊 AMZ**。
- 调用通常**只是用来检查**：现有 SWF 是否适合当前任务。
- 不适合 / 没有 → 构造 TWF。
- **SWF 库的检查者、TWF 的构造者，从不进入执行。**

**待定**：DIR 的隔离边界（它要看整个 SWF 库目录 + 任务本身，比其他盒子看得多）。

## 8. 判断边与输出契约

### 8.1 先缩小问题

路由判断**不需要"结构化整个输出"**，只需要一个**很小的信号**。

→ 真正的设计对象是 **「信号」，不是「输出」**。正文保持自由形式，质量不受损。

### 8.2 判断手段的四级阶梯

| 级 | 手段 | 成本 | 降智 | 适用 |
|---|---|---|---|---|
| **1** | **确定性规则** | 0 | 无 | 产物类型、字段空否、计数、文件是否真生成 |
| **2** | **尾部信号块**（AMZ 自报） | 0 | 极小 | AMZ 能自己判断路由 |
| **3** | **弱模型转码** | 1 次便宜调用 | 无 | AMZ 是黑盒 / 信号块解析失败 |
| **4** | **格式化 pipe AMZ**（短思考链） | 1 次贵调用 | 无 | 判断需要真正的语义理解 |

**硬规则**：

> **每条判断边必须标明属于哪一级；能降到级 1 的不许用级 2。**

**级 1 的覆盖面比想象中大**：写 word 的盒子**产出的成品必然是 docx**，
所以"需要 word"可以退化为**检查上一步的产物类型**，完全不要模型。

**级 2 的正确形态**：

> **正文自由形式 + 尾部一个固定格式的信号块。**

- 降智的真正风险点**不是**"要求结构化"，而是**"要求正文结构化"**（整段 JSON 会挤压表达）。
- 附加好处：判断的稳定性**不再依赖正文措辞**。

**级 4 的价值**：它是**隔离的**，可用极窄 prompt + 固定短思考链，**输出稳定性最好**。留给真正需要语义理解的判断。

### 8.3 判断边文法

```yaml
edge:
  from: plan
  to: write_word
  when: signal.need_word == true
  else: review
```

**求值规则（宿主侧、确定性、无副作用）**：

- 文法限制为 `signal.<field> <op> <literal>`，`op ∈ {==, !=, in, >, <}`，可用 `and / or / not`
- **禁止函数调用、禁止模型参与求值**
- 有分支的边组必须有 `else`

### 8.4 解析失败策略

1. 缺字段 / 类型错 → **走 default 边**（宽松），不要中止
2. 只有"连 default 也不该走"时，才升级到级 3（弱模型补一次）

### 8.5 转码器的归属：全局实现 + 局部声明

| | 全局统一 | SWF 内逐个设计 |
|---|---|---|
| 优点 | 改一次全局生效 | 贴合每条边 |
| 缺点 | 不同 AMZ 输出形态差异巨大，**一刀切必然有一半不合适** | 同一转码方法在 N 个 SWF 里重复定义，**改一次要改 N 处，且会漂移** |

**→ 转码器 = 全局注册的「实现」＋ SWF 内按边声明「选用哪一档」。**

SWF 只写"这条边用 `weak`"，不写"`weak` 是什么模型、什么 prompt"；要覆盖时才在 SWF 里内联定义。

**这个形状 DSH 里已有现成同构**：`compaction-basic` 的实现是**全局**的，preset 决定**要不要装载、配什么阈值**。
**照抄即可，不必发明新的一致性模型。**

## 9. 记忆与标号

### 9.1 结构

```
原始资料 ──[预处理/转换]──▶ 信息段库（编号）
                                  │ 标号
                                  ▼
AMZ:  固定 SystemPrompt + 按标号内联的段 + 诉求 ──▶ 成品
```

**标号 = 已经被转化为模型可读的信息段的序号。**

### 9.2 真正的卖点不是省钱，是避免干扰

长上下文会**稀释注意力**；无关内容不只是占位，是**主动伤害**输出质量。

**但代价是鲁棒性**：

> 盒子里**看不见它"没拿到"的东西**。选错标号或漏标号，盒子**不会说"资料不足"，它会自信地产出错误成品**。

→ **「选标号」这一步的质量 = 整个系统的性能上限。**
→ 因此必须有一道**"资料是否充分"的检查**，放在调用方（AGT/DIR）一侧（盒子内部做不到）。

### 9.3 五个必须定的参数

| 参数 | 决定什么 |
|---|---|
| 谁把原始资料转成模型可读段 | PDF / Word / Excel / 图片 / 网页各有各的转换 |
| **分段粒度** | **段太大 → 隔离失效**（等于把原文塞回去）；**段太小 → 标号爆炸** |
| 编号作用域 | **必须是项目级（跨会话）**，否则资料无法复用、SWF 的"沉淀"打折 |
| 存放位置 | 跨会话、跨项目可用性 |
| 可信等级 | 见 §9.5 |

### 9.4 DSH 现成件

| 用途 | 现成件 |
|---|---|
| **信息段引用机制** | `ctx.spillStore.saveText() → SpillRef` —— 天然的"存文本还引用" |
| 资料摄取 | `attachments`（二进制/图片转模型可读）、`fileReferences`、`session-reference` |

> ⚠ **作用域不匹配**：`dsh-spill-local` 是 **"private session-scoped files"**（会话级），
> 而 LLMR 的资料库必须**项目级**。这一条要改。

### 9.5 新增攻击面：信息段库 → prompt 内联

资料段是被当**可信输入**直接塞进 prompt 的。如果资料带对抗性内容，盒子会被带偏：

- 盒子隔离、工具窄 → **损害有限**（这正是设计的红利）
- 但"写 word 的盒子"可能产出恶意文档；带 `fs` 的盒子可能被诱导写文件

**默认策略**：**入库时查一次**，标记可信等级；内联时不重查（成本考虑）。
外部来源资料默认不可信，复用 DET 已有的 `secPromptDefense`。

## 10. 权限模型（WPC）

**AMZ 与「硬编码工具 + 权限」静态绑定。**

因此：

> **WPC 不是运行时动态控制面，而是设计期的绑定表。**

于是 `tools.restrict` / `tools/pre-execute` 在 LLMR 里的角色从"策略"降级为"**执行保证**"——确保那张绑定的表在运行时真的生效。

### 可审查性：LLMR 相对通用 agent 的结构性优势

> **能力是设计期静态绑定的一张表（AMZ × 工具 × 权限）。一张表就能看清一个陌生 SWF 的全部能力。**

通用 agent 审不了——它运行时才决定调什么。**LLMR 的"固定"不只是为了注意力和成本，它同时带来了可审查性。**

> **这条应写进设计原则。**

## 11. UI 规格

### 11.1 绑定关系（已定）

> **任务判定 → 进入 SWF → AGT 与这个人机交互页面绑定，此后 stable，不再变。**

- **判定之前 = LLMR 里唯一"流动"的阶段**（分级、判性质、大型还要多轮问询）
- **进入 SWF 之后 = 一切固定**：AGT / UI / AMZ / 工具 / 权限 / 流程
- 唯一的例外出口 = DIR 走 TWF 兜底

**AGT 是 SWF 的门面：SWF 定了，AGT 就定了。**

> **已撤回的错误提案**：曾经设想过"UI 随 SWF 内的步骤/AMZ 切换"。
> 那违背了贯穿整个设计的 **固定 + 隔离** 原则——LLMR 里除了 TWF，没有任何东西在运行时变形。

### 11.2 槽位落点（运行时事实）

| 作用域 | 槽位 | 用途 |
|---|---|---|
| root（进程级） | **`sidebar.panellist`**（list, 风险 none）+ **`main`**（keyed, 仅占 `conversation`） | **四个入口 + 中央面板** ← 主落点 |
| root | `shell.overlay` | 浮动层（DET 工具栏已在此） |
| session | `conversation.view`、`conversation.session.header.utilities`、`conversation.composer` | 会话内扩展 |
| session | `sidebar.right.pane.tab`（keyed，**无人占用**） | 右栏标签（WPC 的自然位置） |

**必须避开的**：

- ❌ **不要 shadow `sidebar` / `sidebar.workspaces`** —— `sidebar.workspaces` 就是**会话列表本体**，
  换掉它等于砍掉 DSH 主导航。
- ❌ **`conversation.chat.node` 的 `user` 键已被 DET 占用**，LLMR 别抢。
- ❌ 宿主已占了 `shell.overlay` 与 `sidebar.footer.action` 上的若干槽位。

### 11.3 多会话并发（已解除）

每个会话有自己的 AGT，各自绑自己的页面，**root 级跟随当前聚焦的会话**即可。
不存在冲突，也不需要按步骤切。

### 11.4 兜底

- **没有合适的页面 → 回退 DSH 原生 UI**（LLMR 完全不介入）。与"小型任务零介入"同构。
- **逃生门**（任务中途性质变了）：**待定**（见 §16）。

## 12. 校验器规格（第一阶段实现目标）

### 12.1 三个使用者

| 谁用 | 用途 |
|---|---|
| 作者（你） | **发布前门槛** |
| 用户（自己写） | **本地助手**——写完自己先跑一遍 |
| 导入者（拷大佬的） | **安全审查**——审 AMZ × 工具 × 权限表 |

### 12.2 输入 / 输出

```
输入：一份 SWF 声明（§5.1）
输出：① 错误清单（阻断）② 警告清单（提示）③ 能力表面板（AMZ × 工具 × 权限）
```

### 12.3 检查项

| # | 检查 | 级别 |
|---|---|---|
| 1 | 每个 AMZ 的工具表是**能完成任务的最小集**吗（CSP 安全前提） | 警告 |
| 2 | 有分支的边组都有 `else` 吗（失败策略落点） | **错误** |
| 3 | 每条判断边**标明属于哪一级**了吗 | **错误** |
| 4 | 能降到级 1 的边是否被误用级 2+ | 警告 |
| 5 | 引用的 AMZ / 工具 / UI 页面组**本地存在**吗 | **错误** |
| 6 | `output.signal.fields` 与所有引用它的 `when` 表达式**字段一致**吗 | **错误** |
| 7 | 存在**不可达**的 AMZ / 边吗 | 警告 |
| 8 | 存在**无出边且非终态**的 AMZ 吗 | **错误** |
| 9 | 导入的 SWF：**AMZ × 工具 × 权限表**是否已人工过目 | 错误（导入路径） |
| 10 | `step` 型 AMZ 是否被用在"想省钱"的位置（缓存失效） | 警告 |

### 12.4 为什么先做它

**不依赖任何未定项**，且被三方共用。它是整个 LLMR 的最小可用切片。

## 13. 生态与分发

### 13.1 三条来源（全是人，LLMR 自己**不造** SWF）

| 来源 | 谁 | 机制 |
|---|---|---|
| **找我造** | LLMR 作者（你） | 用户提 **issue** → 作者造 |
| **自己写** | LLMR 用户 | 用户用 AI 辅助 + 自己的编程知识写 |
| **拷贝大佬的** | 第三方 | 直接拷 |

### 13.2 三条都指向同一个结论

> **SWF 必须是声明式数据格式，不能是程序。**

- 人写 → 要好写好读（YAML/JSON）
- 用户写 → 要能被 AI 可靠生成、能被 LLM 辅助（结构化的东西才写得稳）
- 拷别人的 → 要能自包含、能校验、能审

**DSH 里已有这个形状**：`agent preset` 就是 YAML 声明，可 `copy` / `read` / `remove`，还能从目录读。**SWF 照它的形状做。**

### 13.3 拷贝路径 = 安全关键路径

拷一个陌生 SWF = **引入别人声明的工具和权限**。这与 DET 全局插件库是**同一类风险**：

> DET 自己写着："全局插件代码以当前进程真实权限运行；`scanCodeWarnings` 只是提示性启发式，**不是安全边界**。"

**审查对象是 `AMZ × 工具 × 权限` 那张表**（详见 §10），不是 prompt。

### 13.4 复用 DET 的现成管道

| 用途 | DET 现成件 |
|---|---|
| 导入管道 | **`det_global_plugin_github_rebuild`** —— "AI 读取源码并自行编写等价插件，注入「病毒/漏洞检查上下文」供你审查，再入库"。**天然带审查步骤。** |
| 发现渠道 | `det_global_plugin_store_search` 四源（github / marketplace / leaderboard / radar） |
| 入库 | `det_global_plugin_github_save` |

## 14. 复用 / 差异化 / 全新

### A. 直接复用

| 用途 | DSH / DET 现成件 |
|---|---|
| 信息段引用 | `ctx.spillStore.saveText() → SpillRef` |
| 资料摄取 | `attachments`、`fileReferences`、`session-reference` |
| 一次性容器执行通道 | DET **`det_tct`**（一次性 + 档位 + 权限白名单 + 用完即焚） |
| AMZ 的 fresh / fork | `subagent` / `subagent_fork` |
| 截取 ③ / ⑤ | `sessions.fork(source, boundary)` / `compaction` |
| WPC 执行保证 | `tools.restrict` / `tools.guard` |
| SCP / TCP 注入 | `systemPrompt.section` / `getSectionOrder` / `systemPrompt.tools` |
| 声明式人工资产格式 | `agentPresets`（YAML、可 copy/read/select） |
| AGT 的 purpose | `goal`（`create_goal`/`get_goal`/`update_goal` + `ui-goal`） |
| WFW 面板对话目录 | `dsh-client-ui-subagent` |
| UI 槽位 | `sidebar.panellist` + `main`(keyed) + `sidebar.right.pane.tab` |
| 导入/发现/审查 | DET 的 rebuild / store_search / save |
| Prompt 攻击防御 | DET `secPromptDefense` |

### B. 必须差异化

| 官方件 | 差异 |
|---|---|
| `workflow` 工具 | 它是**脚本 + spawn-only + 无 per-stage prompt/工具表**；SWF 是**人工固定 + 硬编码条件边 + per-AMZ 固定 prompt/工具** |
| `subagent` 工具 | 它是**模型自主 tool use**；AMZ 是**硬编码 step-to-step**——**方向相反** |
| `compaction-basic` | 它是**被动、会话内**；LLMR 是**主动、跨容器** |
| `agentTeams` 契约 | 概念几乎 1:1（`spawnTeammate(context:'fresh'\|'fork')` ↔ ttc·exp/step；task `blockedBy` ↔ 调用顺序；`writeScopes` ↔ WPC；`remoteView()` ↔ 前端数据源）。**但本机未装载**（无 team 包、无 team 工具）。 |

> **决策建议**：**不依赖 `agentTeams`**，改用 `ctx.subagents.registerProvider` 注册 LLMR 自己的
> AMZ provider（这样能在 spawn 时施加固定的 prompt / 工具 / 模型绑定）。
> 保留"若官方 agentTeams 稳定则迁移"的注记。

### C. 全新

1. **硬编码条件边求值器**（读结构化信号 → 求值 → 激活下一条边）
2. **信息段库**（原始资料 → 模型可读段 → 编号，**项目级**）
3. **SWF 库 + TWF → SWF 晋升流程**
4. **DIR**（检查器 / TWF 构造器）
5. **任务分级入口**（小/中/大）
6. **按 SWF 切换的 UI 宿主**
7. **校验器**（§12）
8. **专用工具盒** —— ⚠ **DSH 里没有 Word / Excel / PPT 工具**

> **关键推论**：AMZ 的价值取决于世上有没有对应的专用工具。
> 没有工具，盒子就只是个"限制得很死的通用模型"，隔离只剩省钱、没有能力增益。
> **AMZ 库本质是能力盒库，盒子里得真装东西**——这部分工作量在"运行时"之外，且不小。

## 15. 插件形态与实施阶段

### 15.1 形态

**LLMR = 常驻插件**（与 DET / DBS / TOPO 同档），由 **Host 半区 + Client 半区**组成：

- **Host 半区**：SWF 加载器、校验器、条件边求值器、信息段库、DIR、TWF、AMZ 的 subagent provider、`llmr_*` 工具
- **Client 半区**：UI 宿主（`sidebar.panellist` + `main` keyed 面板）
- 装载方式：`profiles/web/cordis.patch.yml` + 独立包（同 DET）

> 依据：它**发布服务**（段库、SWF 注册表）→ 属于 **host 组合**；
> 而按会话声明选用（哪个 SWF）→ 属于会话侧。

### 15.2 实施阶段

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **0** | **校验器**——SWF 声明的解析 + §12.3 的 10 项检查 + 能力表面积 | **无** |
| 1 | SWF / AMZ 声明格式 + 加载器（只读、能解析能展示） | 阶段 0 |
| 2 | 硬编码条件边求值器 + 最小 SWF（规划 AMZ → 写 word AMZ，两个盒子） | 阶段 1 |
| 3 | 信息段库 + 标号（项目级） | 阶段 1 |
| 4 | DIR + TWF + 晋升 | 阶段 2、3 |
| 5 | UI 宿主（`sidebar.panellist` + `main` keyed 面板） | 阶段 2 |
| 6 | 生态（导入导出、审查、issue 流程） | 阶段 4、5 |
| 7 | 专用工具盒（docx / xlsx / pptx） | 与上并行 |

| # | 问题 | 我的默认 | 理由 |

| 1 | 四阶梯排序 | **采纳，含硬规则「能降级 1 的不许用级 2」** | 与 LLMR"硬编码取代 tool use"的哲学一致 |

## 附：设计原则（贯穿全文，可单独引用）

1. **固定优先**——SWF 固定、AMZ 固定、工具/权限静态绑定、UI 固定。
   LLMR 里唯一的"流动"是判定之前，唯一的例外是 TWF。
2. **隔离优先**——容器之间互不可见；隔离由"独立会话"结构性提供，不需要额外机制。
3. **硬编码优先于自主**——能用确定性规则就别用模型；能用固定边就别用 tool use。
4. **避免干扰，对模型与用户同样成立**。
5. **可审查性**——能力是设计期的一张静态表，所以陌生 SWF 能被审。
6. **所有可复用实现全局注册，SWF/AMZ 只声明选用**（转码器 / UI / 工具 三者同构）。
7. **能力盒子里得真装东西**——没有专用工具的 AMZ 只有省钱，没有能力增益。
